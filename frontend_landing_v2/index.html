02

The pipeline

How it works

A real data pipeline, not just CRUD. Each step maps to a live endpoint.

  1. 01

    Ingest the upload

    Multipart upload. GPS parsed from binary EXIF, file stored on local disk.

    POST /api/v1/photos/upload
  2. 02

    Name the place

    Nominatim reverse-geocode turns coordinates into city, state, country.

    37.7749, -122.4194 becomes San Francisco
  3. 03

    Book the slot

    Caption, destinations, and a UTC publish time. Stored as a scheduled row.

    PATCH /photos/{id} with status scheduled
  4. 04

    Publish on the tick

    The 60 second worker finds due rows, builds the Meta container, publishes it. Transient errors retry, permanent ones surface as failed.

    POST /photos/{id}/publish
03

State machine

Status lifecycle

One photo, one post. The state machine enforces it.

draft -> scheduled -> published / failed, then retry

Fail fast on formats

JPG and PNG only. Rejected at schedule time, before the worker ever fires, because Instagram accepts nothing else.

Never double post

The button disables in flight and the server answers 409 on already-published. Two rapid clicks cannot create two posts.

Retry the right way

Timeouts and rate limits stay scheduled and retry next tick. Bad tokens and rejected formats move to failed with the Meta message kept verbatim.

Decisions

Why this architecture

Boring on purpose. Each choice removes a server the project does not need yet.

No extra servers

Scheduler without Redis

APScheduler runs in process, one instance max. No queue to operate until multiple users demand it.

Tunnel instead of S3

Meta fetches images over the Cloudflare tunnel. Public HTTPS with no buckets and no storage bill.

Vanilla JS

No build step, no framework to upgrade. The dashboard is static files on the same server.

“Let the type carry the page — the photographs carry themselves.”
